# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

CmdStarter is a layer over System.CommandLine (2.0.14 stable) that turns plain C# code into a CLI tree. In the class model, classes become commands, public properties become options and handler parameters become arguments. In the method model, `[Command]` methods become commands. Both models support Microsoft.Extensions.DependencyInjection. The 2.0 rewrite accepts breaking changes (`docs/adr/0005`, `docs/migration/1.x-to-2.0.md`). Target: .NET 10 only (`global.json`, `ProjectsCommon.props`).

## Commands

Run from the repository root (PowerShell; on this machine Git Bash fails to fork subprocesses).

```powershell
dotnet test CmdStarter.sln -nologo                       # build + all tests; the only trustworthy check
dotnet format whitespace --verify-no-changes             # formatting gate (CI runs it)
dotnet test CmdStarter.sln --filter "FullyQualifiedName~CmdStarter.Tests.Options.IsPropertyFilledWithOption"
dotnet test CmdStarter.sln --filter "TestCategory=REPL"     # fixtures carry [Category(...)]; "Integration" for the process tests
dotnet run -c Release --project benchmarks/CmdStarter.Benchmarks -- --filter * --exporters github   # startup measures
```

- `benchmarks/CmdStarter.Benchmarks` (BenchmarkDotNet 0.15.8, in the solution, no test, no reference from the test projects) measures discovery, tree building and execution on its own 24 commands; `docs/advanced/performance.md` holds the published series. Run it alone: any parallel build or test skews the numbers. Reports go to `BenchmarkDotNet.Artifacts/` (ignored). `GlobalOptionsManager` scans the global options containers once per process (static `foundTypes`), so only the cold-start measure pays for that scan.

- Do not chain `dotnet build` then `dotnet test --no-build`: if the build fails, the old binaries are tested and pass.
- `TreatWarningsAsErrors` is on everywhere; the library also runs the `latest-recommended` analyzers, with no rule disabled (`docs/adr/0008`, `docs/adr/0013`): public constants are PascalCase (`Starter.ExclusionSymbol`, `StarterCommand.OptionPrefix`…), public generic type parameters take the `T` prefix (CA1715), the only CA1031 suppressions are the two catch-all handlers in `Starter`, and the only CA1716 suppression keeps the middleware name `next` on `ICommandFilter.InvokeAsync`.
- Building `CmdStarter.Lib` and `CmdStarter.Hosting` also produces their NuGet packages in `artefacts/` at the repository root (`GeneratePackageOnBuild`). `cints.CmdStarter` ships the Roslyn analyzer `CmdStarter.Analyzers` (netstandard2.0, Microsoft.CodeAnalysis.CSharp 5.0.0) under `analyzers/dotnet/cs`, with no package dependency (`docs/adr/0018`).
- System.CommandLine localizes its help text (French on this machine): tests must check exit codes or symbols, never help wording.

## Architecture

`Starter` (`CmdStarter.Lib/Starter.cs`) runs a lazy three-stage pipeline. Each stage runs once and is invalidated when a filter property changes (`Namespaces`, `Classes` reset everything; `ClassesBuildingMode`, `IsRootingLonelyCommand`, `CommandsTypes` reset the trees):

1. **`FindCommandsTypes`** scans every assembly loaded in the AppDomain for non-abstract classes implementing `IStarterCommand` that have a namespace, then filters them by `Namespaces` (prefix, `~` excludes) and `Classes` (wildcards `?`, `??`, `*`, `**`, `~` excludes; see `Reflection/Helper.cs`). The result is sorted by `FullName` (ordinal), as are the global options types, so the tree and the help never depend on reflection order.
2. **`BuildTree`** builds a `TreeNode<Type>` with `Loader/CommandsTreeBuilder.cs`, from `[Parent]`/`[Children]` attributes, the namespace hierarchy, or both (`ClassesBuildingMode`). Leftover types become top-level commands. `Starter.UseTree(Action<CommandTreeDefinition>)` (`docs/adr/0016`) replaces discovery and placement of class commands: the definition's types are the class commands (no scan, no filter, definition order) and its tree is `CommandsTypesTree`. `CommandTreeDefinition` also defines class-less groups (`Group`, kept as per-type group paths, not tree nodes) and names/aliases (`WithName`, `WithAliases`); `AddLevel` places grouped children after the others, under groups that `ResolveDefinedGroupParent` reuses by name or creates as implicit groups. The definition is closed after `UseTree`; a lonely command with a group path is not rooted. Without a definition, `Starter.GroupsByNamespace` (off by default, ignored in `OnlyAttributes` mode; `docs/adr/0017`) gives the same group paths to top-level class commands without `[Parent]`: their namespace segments after the common base namespace (minus the last one for a command that represents its namespace, i.e. adopted deeper namespaces), so `Users.List` and `Groups.List` become `users list` and `groups list`. Both sources fill the single `groupPaths` dictionary read by `HasGroupPath`/`AddLevel`/`ResolveGroupParent`.
3. **`InstantiateCommands`** is the adapter. `StarterCommand` no longer derives from `Command`: each command type gets a `Binding/CommandRegistration` that links the type, its instance and a System.CommandLine `Command` it builds. `Reflection/Loader.cs` creates options from properties and arguments from the parameters of `HandlingMethod`. Only leaf commands get an action. With a single command type and `IsRootingLonelyCommand`, its symbols go on the root command.

At execution, the action (`HandleCommandAsync`) binds the global options, then the options onto the instance's properties (`Binding/CommandBinder.cs`). It then invokes the `HandlingMethod` delegate through `DynamicInvoke`, inside the chain of **command filters** (`ICommandFilter.InvokeAsync(CommandContext, next)`, `Starter.AddFilter`, `docs/adr/0019`). The first registered filter is outermost. The chain runs after activation and binding, for both models, through the shared `InvokeFiltersAsync`. Its innermost step is the handler, the 130 conversion and `CommandHandled`, so a filter that skips `next` also skips `CommandHandled`. An unavailable command is refused before any filter. A filter registered by type is resolved from the execution scope, else created with `ActivatorUtilities` or its constructor; a filter CmdStarter created is disposed after the execution. `CmdStarterOptions`/`CmdStarterBuilder.AddFilter<T>` also register it as a transient. A returned `int`, `Task` or `Task<int>` becomes the exit code. Parse errors return a non-zero code and never throw (`docs/adr/0007`); an unhandled exception during activation, binding, handling or release writes only its message, on one line, to stderr with exit code 1 (`Starter.ShowExceptionDetails = true` hands it to System.CommandLine, which prints the whole exception); configuration errors derive from `CmdStarterException` and are thrown while the tree is built (`docs/adr/0010`).

Every `Start` goes through `StartCoreAsync`. An execution's **`CommandConsole`** (`docs/adr/0021`) is the console passed to `Start(args, console, token)`, else `Starter.DefaultConsole`. It becomes the invocation configuration's `Output`/`Error`, so help, parse errors and CmdStarter's own messages follow it. It is attached to that `InvocationConfiguration` instance in a `ConditionalWeakTable`, never stored in a field, so nested and simultaneous `Start` calls keep their own console; `CreateInvocationConfiguration` overrides must return a new instance each call. `GetExecutionConsole(parseResult)` reads it back (else `CommandConsole.Standard`, the process streams read now) for a handler parameter of type `CommandConsole` (skipped as an argument like `CancellationToken`, `ParameterBindingKind.Console` in the method model) and for `CommandContext.Console`. Without a console the call is exactly the pre-021 one. `Starter` is still not meant for concurrent `Start` calls (parsed global options are per instance).

Command model:
- A command is a `StarterCommand` subclass or any class implementing `IStarterCommand`. The handler is whatever delegate `HandlingMethod` returns.
- Which properties become options is decided in `Helper.GetProperties`: public read/write properties, filtered by `[Option]`, `[NotOption]` and `[AllOptionsExcluded]`.
- DataAnnotations `ValidationAttribute`s on option properties, handler parameters, method parameters and global options become System.CommandLine validators (`Reflection/Loader.cs`, `docs/adr/0014`). An implicit (defaulted) value and a value that fails conversion are not validated; the latter stays System.CommandLine's parse error. `[Required]` still also sets `Option.Required`.
- Names are kebab-cased from the type and property names.
- At the end of `InstantiateCommands`, `Loader/SymbolNamesValidator` throws `InvalidAttributeException` when a command, its direct subcommands (the root's name, i.e. the executable, included) or the options declared on one command (built-in help and version included) share a name or alias. System.CommandLine would otherwise throw a raw `ArgumentException` only when parsing reaches that branch, or silently ignore the second option. Shadowing a recursive (global) option from a subcommand is not checked.
- An option property's initial value (read from the description instance, or from a throwaway instance of a global options container) becomes its `DefaultValueFactory` (`Loader.SetImplicitDefault`), so the help shows it; skipped for `null`, empty strings and collections, the type's default value and `[Required]` options. System.CommandLine gives every `Option<bool>` its own implicit `false` default, so before this a `bool` property initialized to `true` was reset to `false` when omitted.
- Global options are classes implementing `IGlobalOptionsContainer`. `GlobalOptionsManager` finds them (static cache over all assemblies) and adds them as recursive options on the root. It rebuilds them at each parse; commands read them with `GetGlobalOptions<T>()`.

Instantiation (`docs/adr/0006`): `Starter.Activate` creates every instance. Its priority order is:
1. a static `GetInstance<T>()` declared by the command type;
2. `Starter.ServiceProvider` (Microsoft DI, one `AsyncServiceScope` per execution);
3. the per-`Starter` factory (`SetFactory`, the way to plug in another container, as `CmdStarter.Demo.SimpleInjector` does; `IServiceManager` and `Start(IServiceManager, …)` are `[Obsolete]`, and only `ServiceManager.cs` and one `CommandsResults` test silence CS0618);
4. the parameterless constructor.

Each command type gets one **description instance**, created when the tree is built. It is used only to read metadata (name, `HandlingMethod` signature, initial option values), it is released at the end of `InstantiateCommands`, and `FindCommandInstance` returns it. Each execution creates a fresh instance inside `HandleCommandAsync` and releases it with `Binding/CommandActivation` (`await using`), even when the handler throws. `CommandHandled` exposes that instance before it is released. `CmdStarterBuilder` and `CmdStarterApp` wrap all of this for Microsoft DI, with `ValidateScopes` and `ValidateOnBuild` on. The builder delegates to `IServiceCollection.AddCmdStarter(Action<CmdStarterOptions>)` (core, no extra dependency): it creates the `Starter` (or `ReplStarter`), runs `FindCommandsTypes`, registers the command types as transients and the `Starter` as a singleton factory that sets the root provider as `ServiceProvider` (`??=`). The separate `CmdStarter.Hosting` project/package, the only one that depends on Microsoft.Extensions.Hosting, adds `IHostApplicationBuilder.AddCmdStarter` (replaces `ConsoleLifetime` with a silent `CmdStarterHostLifetime`) and `IHost.RunCmdStarterAsync(args)` (starts and stops hosted services around the command or the REPL, token linked to `ApplicationStopping`; `docs/adr/0015`).

**Method model** (`docs/adr/0009`) runs alongside the class model:
- **Discovery**: `[Command]` (`Attributes/CommandAttribute`) goes on public methods. A class marked `[Command("group")]` becomes a group node under the root; otherwise its methods become top-level commands. A group or method name can be a space-separated path (`[Command("admin users")]`): each segment but the last resolves to an existing subcommand (class command, group, even a leaf) or else to a new **implicit group** (no action, no state metadata, kept in `implicitMethodGroups`), which a later explicit group of the same name adopts (two explicit groups on the same path still throw). Discovery (`Loader/MethodCommandsLoader`) fills `Starter.MethodCommandsTypes`, scanning only assemblies that reference CmdStarter.Lib. `InstantiateCommands` adds these nodes after the class tree and throws `InvalidAttributeException` for invalid definitions.
- **Parameters** are classified when the tree is built (`Binding/ParameterBinding`): `CancellationToken`, then global options containers, then `[FromServices]`, then `[Option]`, then services that `ServiceProvider` reports through `IServiceProviderIsService`; anything else is a positional argument.
- **Execution**: each run gets a fresh declaring-class instance (none for static methods) and, with Microsoft DI, its own scope (`ActivateMethodCommand`). `SetFactory` and `GetInstance` do not apply to this model.
- **Lonely rooting** only happens when there is no method command.

`Repl/ReplStarter` derives from `Starter` and loops over `IReplInputProvider.GetInputAsync` (`docs/adr/0011`):
- `null` ends the loop, and blank lines are skipped.
- The built-in words `ExitCommands` (`exit`, `quit`) and `HelpCommands` (`help [command]` → `--help`) take precedence over application commands.
- Every line is a **command sequence** (`docs/adr/0022`): `Sequences/CommandSequence.TryParse` splits it on `;`, `&&`, `||` outside double quotes, and the internal `ExecuteAsync` runs the steps with shell semantics (last executed code, 130 stops). Each step is a **text pipe** (`docs/adr/0023`): a single `|` splits it into `CommandSequenceStep.Pipeline`, and `Starter.RunPipelineAsync` runs a one-command pipeline unchanged (no console forced) and a longer one buffered (each command's output in a `StringWriter`, read back as the next one's `In`; errors straight to the execution console; the last command's code; 130 stops). Each command goes through `RunReplStepAsync`, where `exit`/`help` keep their meaning (`exit` in a multi-command pipeline is refused with code 1), then `Start(command[, console], token)`, which raises `OnCommandExecuted`. A line without any operator runs exactly as before, even when `TryParse` rejects it (an unclosed quote). `Starter.StartSequence` and `Starter.SequenceOption` (off by default; `app -c "a; b"`, checked against root options and top-level command names by `SymbolNamesValidator`; its setter resets the trees) run sequences outside the REPL. `ReplStarter` re-declares `StartSequence` and checks `SequenceOption` in its own `Start(string[])` so every step raises the event (duplication noted as debt for the review).
- Each command runs with its own linked token, so Ctrl+C (`Console.CancelKeyPress`, with System.CommandLine's own handling switched off through `CreateInvocationConfiguration`) or `CancelCurrentCommand()` cancels that command only.
- A cancelled command returns 130. Class-model handlers can take a `CancellationToken` parameter, which is not turned into an argument.
- `CmdStarterBuilder.UseRepl` plus `CmdStarterApp.RunReplAsync` give the REPL Microsoft DI with one scope per command. The builder registers the `Starter` (and the `ReplStarter`) as singleton services.
- `ConsoleReplProvider` reads through one `Repl/ReplLineEditor` per session (history, Tab completion; `docs/adr/0020`) unless `LineEditing` is off or stdin or stdout is redirected, which keeps the raw `ReadLineAsync` path the process tests rely on. The editor takes a `Func<ConsoleKeyInfo>`, so `ReplLineEditing` tests drive it with simulated keys. Completions come from `ReplStarter.GetCompletions`: System.CommandLine's completions after `UpdateCommandAvailability` (hidden commands are not proposed), plus the built-in words in the first word, computed on the sequence step that holds the cursor (`CommandSequence.FindStep`, which shares `Scan` with `TryParse` and accepts unfinished lines); the editor's current word starts after the last white space, `;`, `&` or `|`. The `ReplStarter` constructors hand it to a `ConsoleReplProvider` that has no `CompletionSource`.

**Command states** (`docs/adr/0012`) work with or without the REPL.
- The library defines no state. A command (class, method group or method) carries `[AvailableInState(...)]` with the application's own values, and the application exposes its current state through `ICommandStateProvider`. The provider comes from `Starter.StateProvider`, or else from `ServiceProvider` (register it as a singleton).
- Before each `Start`, `UpdateCommandAvailability` asks for the current state:
  - an unavailable command, and its whole subtree, gets `Hidden` (combined with `[Hidden]`);
  - typing it anyway returns 1 with "Command '…' is not available in the current state.";
  - the tree is not rebuilt;
  - the rooted lonely command is refused but never unhidden;
  - commands the application added to `RootCommand` itself are left alone.
- The attribute without any provider throws `InvalidAttributeException` when the tree is built.

**Analyzer** (`CmdStarter.Analyzers`, `docs/adr/0018`): rules `CMDS0001`–`CMDS0011` repeat at compile time checks the runtime already makes (parent cycles, several `[Parent]`, `[AutoComplete]` that yields nothing or uses an unsupported type, blank command names, invalid `[Command]` methods, mixed models, empty `[Command]` groups); `CMDS0012` (a command option hides a global option) and `CMDS0013` (a global options container has no option) are advice only. All are warnings, so with `TreatWarningsAsErrors` they break the build of `CmdStarter.Tests.App` and of every project under `samples/` (`samples/Directory.Build.props` references the analyzer). `NameConversion` copies the library's kebab-casing; keep the two in sync (the `KebabCaseMatchesLibrary` test compares them). New rules go in `AnalyzerReleases.Unshipped.md`.

## Tests

- `CmdStarter.Analyzers.Tests` compiles C# snippets against the library (`AnalyzerRunner`) and counts the diagnostics per rule.
- `CmdStarter.Tests` (NUnit) exercises commands defined in `CmdStarter.Tests.Commands`; `CmdStarter.Tests.Common` holds the shared interfaces and the generic `[TestCase<T>]` attributes.
- **The namespaces and attributes of the test commands are test data.** Tree-building tests depend on where a command class lives, so moving or adding a class in `CmdStarter.Tests.Commands` can change other tests' trees.
- Each test isolates its commands by setting `Namespaces`/`Classes` on a fresh `Starter`. `TestsCommon.CreateCmdStarter()` excludes the `Erroneous`, `DepencendyInjection`, `Lifecycle`, `Methods`, `Cancellation`, `ReplApp`, `States`, `Validation`, `MethodGroups`, `Hosting`, `SameLeafNames`, `DefaultValues`, `FluentTree`, `NamespaceGroups`, `Filters`, `Consoles` and `Sequences` namespaces by default (a new namespace of special-purpose test commands is added to both lists) (exclusions also repeated in `Repl.SetDefaultNamespaces`). The lifecycle and DI tests instead isolate one command type with a `Classes` filter, which makes it a lonely, rooted command.
- Command test classes must expose read-only public properties unless the property is meant to be an option: any setter, even a private one, makes `Helper.GetProperties` turn the property into an option.
- Discovery only sees loaded assemblies, so fixtures call `TestsCommon.GlobalSetup()`, which forces `CmdStarter.Tests.Commands` to load (`DirectoryCatalog`). That catalog loads every DLL in the test output folder, so any command assembly copied there joins every default discovery.
- `CmdStarter.Tests.App` is a real CLI app (class and method commands, Microsoft DI) that `Integration/AppProcessTests` runs as a separate process (`dotnet <dll>`) to check exit codes, stdout and stderr. The test project references it with `ReferenceOutputAssembly="false"` (build order only), for the reason above.
- `samples/` holds the documented examples, one runnable project each (`samples/README.md`). `Integration/SamplesTests` and `Integration/DemosTests` run them the same way through `Integration/AppRunner` (project path relative to the repository root, optional environment variables; `RunWithInputAsync` writes stdin, then closes it, for REPL apps), so every new sample or demo needs a `ReferenceOutputAssembly="false"` reference in `CmdStarter.Tests.csproj`. `samples/CmdStarter.Samples.Testing.Tests` is a second NUnit project, run by the same `dotnet test CmdStarter.sln`.

## Conventions

- File-scoped namespaces only (`namespace X;`), enforced by `.editorconfig`. Namespaces: `CyberInternauts.CmdStarter` for the library (assembly `CmdStarter.Lib`, package `cints.CmdStarter`), `CyberInternauts.CmdStarter.<Project>` for the other projects (`Tests`, `Tests.Commands`, `Demo.SimpleInjector`…), so test namespace filters use these names.
- Ordinal string comparisons in the library.
- Architecture decisions are recorded in `docs/adr/` (index in `docs/adr/README.md`); breaking changes go in `docs/migration/1.x-to-2.0.md`.
