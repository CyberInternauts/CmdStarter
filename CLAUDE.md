# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

CmdStarter is a layer over System.CommandLine (2.0.14 stable) that turns plain C# code into a CLI tree. In the class model, classes become commands, public properties become options and handler parameters become arguments. In the method model, `[Command]` methods become commands. Both models support Microsoft.Extensions.DependencyInjection. The rewrite ships as version 1.0.0, not 2.0: only 0.9 betas were ever published (`docs/adr/0030`; in the earlier ADRs "2.0" names this release and "3.0" the next major version, now 2.0). It accepts breaking changes (`docs/adr/0005`, `docs/migration/0.9-to-1.0.md`). Target: .NET 10 only (`global.json`, `ProjectsCommon.props`).

## Architecture

`Starter` (`CmdStarter.Lib/Starter.cs`) runs a lazy three-stage pipeline. Each stage runs once and is invalidated when a filter property changes (`Namespaces`, `Classes` reset everything; `ClassesBuildingMode`, `IsRootingLonelyCommand`, `CommandsTypes` reset the trees). The `CommandsTypes` setter first checks every type (a non-abstract `IStarterCommand` class with a namespace, listed once, else `ArgumentException` and nothing changes); before the first discovery a non-empty list stands for the discovery of the class commands (so no method commands), after it only the class commands change, and an empty list goes back to the discovery (`CommandsTypesSetter` tests). Internal paths write the `commandsTypes` field, never the setter. A stage that throws resets its own state (`ResetCommands()` for discovery, `ResetTrees()` for the tree and the instantiation, which also replaces `RootCommand`), so the next `Start` throws the same configuration error instead of running on a half-built tree (`FailedConstruction` tests):

1. **`FindCommandsTypes`** searches `Assemblies`, else every assembly loaded in the AppDomain, assembly by assembly (`Catalog/CatalogReader.TryRead(assembly, useCatalogs, …)`, shared with `GlobalOptionsManager.FindTypes`; `docs/adr/0027`): an assembly with `[assembly: CommandCatalog]` and `UseCommandCatalogs` (default `true`, setter resets the discovery) is read from its catalog (no `GetLoadableTypes`, no `GetReferencedAssemblies`); any other is scanned (through `Helper.GetLoadableTypes`, which skips the types of an assembly that fail to load instead of failing discovery; dynamic assemblies are read like the others). The internal switch `Starter.DynamicCodeSupported` (`RuntimeFeature.IsDynamicCodeSupported`, set by tests through the IVT) decides how: when true, the attribute is read only on the Lib or an assembly that references it (`CatalogReader.ReferencesLibrary`, asked once per assembly and reused for the method scan), so a satellite assembly is never read; when false (Native AOT), only catalogs are read, nothing is scanned and `GetReferencedAssemblies` is never called, and `UseCommandCatalogs = false` throws a `CmdStarterException` ("Command catalogs are off …"). An assembly whose attributes fail to load (`FileNotFoundException`, `FileLoadException`, `TypeLoadException`) counts as without catalog. Without dynamic code, `MethodCommandsLoader.GetCommandMethods` keeps the `GetMethods` order (no `MetadataToken`). The scan predicate (non-abstract classes implementing `IStarterCommand` that have a namespace, plus the plain commands with a namespace, whose predicate is evaluated only on the method candidates (assemblies that reference the library, a catalog's `AddMethodCommands`) and on a catalog's `AddCommand<T>` types, never on every type of every assembly) then applies to both sources, so a catalog cannot add a type the scan would not find; a catalog that cannot be created or whose `Describe` throws is an `InvalidAttributeException` (OOM excepted). Then the types are filtered by `Namespaces` (prefix, `~` excludes) and `Classes` (wildcards `?`, `??`, `*`, `**`, `~` excludes; see `Reflection/Helper.cs`). The result is sorted by `FullName` (ordinal), as are the global options types, so the tree and the help never depend on reflection order. The catalog brings no measurable speed on CoreCLR (two series in `performance.md`): it is the first step towards trimming and Native AOT.
2. **`BuildTree`** builds a `TreeNode<Type>` with `Loader/CommandsTreeBuilder.cs`, from `[Parent]`/`[Children]` attributes, the namespace hierarchy, or both (`ClassesBuildingMode`). Leftover types become top-level commands. `Starter.UseTree(Action<CommandTreeDefinition>)` (`docs/adr/0016`) replaces discovery and placement of class commands: the definition's types are the class commands (no scan, no filter, definition order) and its tree is `CommandsTypesTree`. `CommandTreeDefinition` also defines class-less groups (`Group`, kept as per-type group paths, not tree nodes) and names/aliases (`WithName`, `WithAliases`); `AddLevel` places grouped children after the others, under groups that `ResolveDefinedGroupParent` reuses by name or creates as implicit groups. The definition is closed after `UseTree`; a lonely command with a group path is not rooted. Without a definition, `Starter.GroupsByNamespace` (off by default, ignored in `OnlyAttributes` mode; `docs/adr/0017`) gives the same group paths to top-level class commands without `[Parent]`: their namespace segments after the common base namespace (minus the last one for a command that represents its namespace, i.e. adopted deeper namespaces), so `Users.List` and `Groups.List` become `users list` and `groups list`. Both sources fill the single `groupPaths` dictionary read by `HasGroupPath`/`AddLevel`/`ResolveGroupParent`.
3. **`InstantiateCommands`** is the adapter. `StarterCommand` no longer derives from `Command`: each command type gets a `Binding/CommandRegistration` that links the type, its instance and a System.CommandLine `Command` it builds. `Reflection/Loader.cs` creates options from properties and arguments from the parameters of `HandlingMethod`. Every typed symbol (`Option<T>`, `Argument<T>`, their default, `ParseResult.GetValue<T>`, the default of a value type) goes through `Catalog/SymbolFactories.For(type)` (`docs/adr/0028`): an `ISymbolFactory` registered by a catalog's `AddSymbolType<T>()` (first registration wins, and replaces a fallback), else a fallback `SymbolFactory<T>` built once by reflection (`CreateFallback`, the only `MakeGenericType` left with `Helper.SearchGetInstanceMethod`'s `MakeGenericMethod`). `DefaultValue` is what `Activator.CreateInstance` gives (a struct's explicit parameterless constructor runs). Nothing observable changes on CoreCLR. Only leaf commands get an action. With a single command type and `IsRootingLonelyCommand`, its symbols go on the root command.

At execution, the action (`HandleCommandAsync`) binds the global options, then the options onto the instance's properties (`Binding/CommandBinder.cs`). It then invokes the `HandlingMethod` delegate through `DynamicInvoke`, inside the chain of **command filters** (`ICommandFilter.InvokeAsync(CommandContext, next)`, `Starter.AddFilter`, `docs/adr/0019`). The first registered filter is outermost. The chain runs after activation and binding, for both models, through the shared `InvokeFiltersAsync`. Its innermost step is the handler, the 130 conversion and `CommandHandled`, so a filter that skips `next` also skips `CommandHandled`. An unavailable command is refused before any filter. A filter registered by type is resolved from the execution scope, else created with `ActivatorUtilities` or its constructor; a filter CmdStarter created is disposed after the execution. `CmdStarterOptions`/`CmdStarterBuilder.AddFilter<T>` also register it as a transient. A returned `int`, `Task` or `Task<int>` becomes the exit code. Parse errors return a non-zero code and never throw (`docs/adr/0007`); an unhandled exception during activation, binding, handling or release writes only its message, on one line, to stderr with exit code 1 (`Starter.ShowExceptionDetails = true` hands it to System.CommandLine, which prints the whole exception); configuration errors derive from `CmdStarterException` and are thrown while the tree is built (`docs/adr/0010`).

Every `Start` goes through `StartCoreAsync`, which runs `StartInvocationAsync` inside the `private protected virtual InvokeCommandAsync`, the single point `ReplStarter` overrides. An execution's **`CommandConsole`** (`docs/adr/0021`) is the console passed to `Start(args, console, token)`, else `Starter.DefaultConsole`. It becomes the invocation configuration's `Output`/`Error`, so help, parse errors and CmdStarter's own messages follow it. It is attached to that `InvocationConfiguration` instance in a `ConditionalWeakTable`, never stored in a field, so nested and simultaneous `Start` calls keep their own console; `CreateInvocationConfiguration` overrides must return a new instance each call. `GetExecutionConsole(parseResult)` reads it back (else `CommandConsole.Standard`, the process streams read now) for a handler parameter of type `CommandConsole` (skipped as an argument like `CancellationToken`, `ParameterBindingKind.Console` in the method model) and for `CommandContext.Console`. Without a console the call is exactly the pre-021 one. `Starter` is still not meant for concurrent `Start` calls (parsed global options are per instance).

Command model:
- A command is a `StarterCommand` subclass or any class implementing `IStarterCommand`. The handler is whatever delegate `HandlingMethod` returns.
- A **plain command** (`docs/adr/0032`, lot 037) is a command of the class model with no base class or interface of CmdStarter: a concrete class with a namespace, without open generic parameters, not `IStarterCommand`, marked `[Command]` and declaring no `[Command]` method (`Helper.IsPlainCommand`, internal; Roslyn twin `CmdStarter.Analyzers/PlainCommands.cs`, keep the two in sync: Roslyn does not mark a static class as abstract, as reflection does, so the twin tests `IsStatic` too, else the generator would write `AddCommand<T>` of a static class, CS0718). Its handler (`MethodCommandsLoader.GetPlainCommandMethod`, checked in `CreateCommand` at every placement) is the method that `[Command(Handler = nameof(...))]` names (public instance, declared or inherited, not of `object`; ambiguous, missing, private or static → `InvalidAttributeException`), else its only public instance method declared by itself, not counting the redefinitions of `object` members, the parameterless `Dispose`/`DisposeAsync` of a disposable class and `[CompilerGenerated]` methods; generic or `ref`/`out`/`in` is refused (`ValidateShape`, shared with `Validate`). Its parameters follow the method model (`ClassifyParameters`: token, console, container, `[FromServices]`, `[Option]`, known service, else argument; values by `BuildHandlerValues`; both shared with method commands) and it runs through `MethodInfo.Invoke` (`CommandRegistration.PlainMethod`/`PlainParameters`, unset for an `IStarterCommand` class, which keeps `LoadArguments`/`InvokeHandlerAsync`). Name: `[Command("name")]` through `ToCommandName`, a single segment (space or blank → `InvalidAttributeException`), else the kebab-cased class name; `UseTree`'s `WithName` wins. No `GetInstance` (`Activate` and `DeclaresGetInstance` only ask `FindGetInstanceMethod` for `IStarterCommand` types, whose `MakeGenericMethod` would break the constraint) and no `GetGlobalOptions<T>()`. `CommandRegistration.DescriptionInstance` and `FindCommandInstance(Command)` are `object`. `FindCommand<T>`, `GetFullCommandString<T>`, `CommandTreeDefinition.Add<T>` and `ParentAttribute<T>` have no constraint (they only use `typeof(T)`, and generic code constrained by `IStarterCommand` alone must still compile: an interface constraint does not imply a class); `FindCommandInstance<T>` and `AddCommand<T>` keep `class`. A static, abstract or open generic `[Command]` class without `[Command]` methods stays a method group (refused as empty); an `IStarterCommand` class marked `[Command]` is refused (both models).
- Which properties become options is decided in `Helper.GetProperties`: public read/write properties (for an `IStarterCommand` class, those declared by types that implement it, except the interface's own; for a plain command, all of them, base classes included), filtered by `[Option]`, `[NotOption]` and `[AllOptionsExcluded]`.
- DataAnnotations `ValidationAttribute`s on option properties, handler parameters, method parameters and global options become System.CommandLine validators (`Reflection/Loader.cs`, `docs/adr/0014`). An implicit (defaulted) value and a value that fails conversion are not validated; the latter stays System.CommandLine's parse error. For an argument, absence is read from its tokens: System.CommandLine marks an argument result implicit only once its default value is materialized (an option is implicit from the start). `[Required]` still also sets `Option.Required`.
- Names are kebab-cased from the type and property names.
- At the end of `InstantiateCommands`, `Loader/SymbolNamesValidator` throws `InvalidAttributeException` when a command, its direct subcommands (the root's name, i.e. the executable, included) or the options declared on one command (built-in help and version included) share a name or alias. System.CommandLine would otherwise throw a raw `ArgumentException` only when parsing reaches that branch, or silently ignore the second option. Shadowing a recursive (global) option from a subcommand is not checked.
- An option property's initial value (read from the description instance, or from a throwaway instance of a global options container) becomes its `DefaultValueFactory` (`Loader.SetImplicitDefault`), so the help shows it; skipped for `null`, empty strings and collections, the type's default value and `[Required]` options. System.CommandLine gives every `Option<bool>` its own implicit `false` default, so before this a `bool` property initialized to `true` was reset to `false` when omitted.
- Global options are classes implementing `IGlobalOptionsContainer`. `GlobalOptionsManager` finds them (static cache over all assemblies, filled at the first `FilterTypes`, never in the `Starter` constructor, with that first `Starter`'s `UseCommandCatalogs`) and adds them as recursive options on the root. It rebuilds them at each parse; commands read them with `GetGlobalOptions<T>()`. The containers pass the `Assemblies`/`Namespaces`/`Classes` filters too, and `GlobalOptionsManager.FilterTypes()` runs before any command is created (lot 037; it reads the starter's settings, never the tree): a method or plain-command parameter that asks for a container the filters exclude throws `InvalidAttributeException` when the tree is built.

Instantiation (`docs/adr/0006`): `Starter.Activate` creates every instance. Its priority order is:
1. a static `GetInstance<T>()` declared by the command type, an `IStarterCommand` one only (since the ADR 0006 amendment of lot 033, when `ServiceProvider` is set its execution still gets the execution scope through `ActivateFromGetInstance`/`OpenExecutionScope`, so filters registered by type get their services and `CommandContext.Services` is not null; `Filters.cs` tests, scope counter `CountingScopes`);
2. `Starter.ServiceProvider` (Microsoft DI, one `AsyncServiceScope` per execution);
3. the per-`Starter` factory (`SetFactory(Func<Type, object>)`, lot 037: an instance that is not of the command type throws `InvalidOperationException`; the way to plug in another container, as `CmdStarter.Demo.SimpleInjector` does; `IServiceManager` and `Start(IServiceManager, …)` were removed before 1.0, lot 035);
4. the parameterless constructor.

Each command type gets one **description instance**, created when the tree is built. It is used only to read metadata (name, `HandlingMethod` signature, initial option values), it is released at the end of the instantiation, and `FindCommandInstance` returns it. `InstantiateCommands` (sync, blocks on an `IAsyncDisposable`-only description) and `InstantiateCommandsAsync` (awaits `DisposeAsync`) share `InstantiateCommandsCore` and the same `hasToInstantiate` guard; `StartInvocationAsync` uses the async one, `ReplStarter.GetCompletions` the sync one. The `GetInstance` lookup (`Helper.FindGetInstanceMethod`) is cached per type (static, never invalidated); `ActivatorUtilities.CreateInstance` is deliberately not replaced by a cached `CreateFactory`, which cannot pick between two constructors (`Lifecycle` two-constructor tests guard this). Each execution creates a fresh instance inside `HandleCommandAsync` and releases it with `Binding/CommandActivation` (`await using`), even when the handler throws. `CommandHandled` exposes that instance before it is released. `CmdStarterBuilder` and `CmdStarterApp` wrap all of this for Microsoft DI, with `ValidateScopes` and `ValidateOnBuild` on. The builder delegates to `IServiceCollection.AddCmdStarter(Action<CmdStarterOptions>)` (core, no extra dependency): it creates the `Starter` (or `ReplStarter`), runs `FindCommandsTypes`, registers the command types as transients and the `Starter` as a singleton factory that sets the root provider as `ServiceProvider` (`??=`). The separate `CmdStarter.Hosting` project/package, the only one that depends on Microsoft.Extensions.Hosting, adds `IHostApplicationBuilder.AddCmdStarter` (replaces `ConsoleLifetime` with a silent `CmdStarterHostLifetime`) and `IHost.RunCmdStarterAsync(args)` (starts and stops hosted services around the command or the REPL, token linked to `ApplicationStopping`; `docs/adr/0015`).

**Method model** (`docs/adr/0009`) runs alongside the class model:
- **Discovery**: `[Command]` (`Attributes/CommandAttribute`) goes on public methods. A class marked `[Command("group")]` that declares `[Command]` methods becomes a group node under the root; otherwise its methods become top-level commands. A concrete `[Command]` class that declares none is a plain command of the class model (see the command model above), and `Handler` on a group or on a method is refused. A group or method name can be a space-separated path (`[Command("admin users")]`): each segment but the last resolves to an existing subcommand (class command, group, even a leaf) or else to a new **implicit group** (no action, no state metadata, kept in `implicitMethodGroups`), which a later explicit group of the same name adopts (two explicit groups on the same path still throw). Discovery (`Loader/MethodCommandsLoader`) fills `Starter.MethodCommandsTypes`, scanning only assemblies that reference CmdStarter.Lib. `InstantiateCommands` adds these nodes after the class tree and throws `InvalidAttributeException` for invalid definitions.
- **Parameters** are classified when the tree is built (`Binding/ParameterBinding`): `CancellationToken`, then global options containers, then `[FromServices]`, then `[Option]`, then services that `ServiceProvider` reports through `IServiceProviderIsService`; anything else is a positional argument.
- **Execution**: each run gets a fresh declaring-class instance (none for static methods) and, with Microsoft DI, its own scope (`ActivateMethodCommand`). `SetFactory` and `GetInstance` do not apply to this model.
- **Lonely rooting** only happens when there is no method command.

`Repl/ReplStarter` derives from `Starter` and loops over `IReplInputProvider.GetInputAsync` (`docs/adr/0011`):
- `null` ends the loop, and blank lines are skipped.
- The built-in words `ExitCommands` (`exit`, `quit`) and `HelpCommands` (`help [command]` → `--help`) take precedence over application commands.
- Every line is a **command sequence** (`docs/adr/0022`): `Sequences/CommandSequence.TryParse` splits it on `;`, `&&`, `||` outside double quotes, and the internal `ExecuteAsync` runs the steps with shell semantics (last executed code, 130 stops). Each step is a **text pipe** (`docs/adr/0023`): a single `|` splits it into `CommandSequenceStep.Pipeline`, and `Starter.RunPipelineAsync` runs a one-command pipeline unchanged (no console forced) and a longer one buffered (each command's output in a `StringWriter`, read back as the next one's `In`; errors straight to the execution console; the last command's code; 130 stops). Each command goes through `RunReplStepAsync`, where `exit`/`help` keep their meaning (`exit` in a multi-command pipeline is refused with code 1), then `Start(command[, console], token)`, which raises `OnCommandExecuted`. A line without any operator runs exactly as before, even when `TryParse` rejects it (an unclosed quote). `Starter.StartSequence` and `Starter.SequenceOption` (off by default; `app -c "a; b"`, checked against root options and top-level command names by `SymbolNamesValidator`; its setter resets the trees) run sequences outside the REPL. `ReplStarter` declares no `Start`/`StartSequence` of its own: it overrides `InvokeCommandAsync`, so every executed command (each step of a sequence, each command of a pipe, nested calls) raises `OnCommandExecuted`, even through a reference typed `Starter` (`docs/adr/0022` amended).
- Each command runs with its own linked token, so Ctrl+C (`Console.CancelKeyPress`, with System.CommandLine's own handling switched off through `CreateInvocationConfiguration`) or `CancelCurrentCommand()` cancels that command only. The running commands are a list under `commandLock` and `CancelCurrentCommand` cancels the last one, so after a nested `Start` it reaches the outer command again, and overlapping `Start`s never leave a released source behind. At the prompt (lot 038, `docs/adr/0020` and `0011` amended), with the line editor, Ctrl+C is a key: `ConsoleReplProvider` sets `Console.TreatControlCAsInput` around `editor.ReadLine` and restores the value it had (not `false`), and the editor rewrites the rest of the line from the cursor, writes `^C` and a new prompt, forgets the draft and puts the history position back at its end (nothing enters the history); a running command still gets the signal (130). Without the editor (`LineEditing` off, stdin or stdout redirected), Ctrl+C at the prompt still ends the process (measured: the read returns `null` before the handler runs, so it cannot be told from Ctrl+Z). On Windows Ctrl+Break stays the signal that ends the process; on Linux and macOS .NET switches ISIG off as a whole, so at the prompt Ctrl+\ is an ignored key and Ctrl+Z follows the editor's end-of-input rule instead of suspending. A console's mode outlives the process, so while the line is read two `PosixSignalRegistration`s (SIGQUIT, i.e. Ctrl+Break on Windows, and SIGTERM) restore it before the process ends, without cancelling the signal; they are released with the read (without them, a REPL killed at the prompt left the shell with Ctrl+C as a key; `AppDomain.ProcessExit` is not raised on SIGTERM on Linux). SIGKILL and `taskkill /F` let no handler run. A real Ctrl+C or signal cannot be tested in memory (`coverage/justifications.md`, `ConsoleReplProvider.cs:47`): it was checked by hand in a pseudo-console (ConPTY) and a Linux pty, including that the console reads `TreatControlCAsInput` false again after Ctrl+Break and keeps `isig` after SIGTERM.
- A cancelled command returns 130. Class-model handlers can take a `CancellationToken` parameter, which is not turned into an argument.
- `CmdStarterBuilder.UseRepl` plus `CmdStarterApp.RunReplAsync` give the REPL Microsoft DI with one scope per command. The builder registers the `Starter` (and the `ReplStarter`) as singleton services.
- `ConsoleReplProvider` reads through one `Repl/ReplLineEditor` per session (history, Tab completion; `docs/adr/0020`) unless `LineEditing` is off or stdin or stdout is redirected, which keeps the raw `ReadLineAsync` path the process tests rely on. The editor takes a `Func<ConsoleKeyInfo>`, so `ReplLineEditing` tests drive it with simulated keys. Completions come from `ReplStarter.GetCompletions`: System.CommandLine's completions after `UpdateCommandAvailability` (hidden commands are not proposed), plus the built-in words in the first word, computed on the sequence step that holds the cursor (`CommandSequence.FindStep`, which shares `Scan` with `TryParse` and accepts unfinished lines); the editor's current word starts after the last white space, `;`, `&` or `|`. The `ReplStarter` constructors hand it to a `ConsoleReplProvider` that has no `CompletionSource`.
- The loop body is `ReplStarter.ExecuteLineAsync` (internal, returns `ReplLineResult(ExitCode, EndsSession)`), which `Repl/Remote/ReplPipeServer` also calls (`docs/adr/0024`): a named pipe (`CurrentUserOnly`, one instance, so one session at a time), a fresh `ReplStarter` per session from the application's factory (the same instance as the previous session, or one whose `Launch` loop runs (`IsLaunched`), throws `InvalidOperationException` out of `RunAsync`), each session opens with the line `R` (`ReplPipeServer.Announcement`, written after the factory and the shared-session check, so a configuration error never announces), then `DefaultConsole` = `TextReader.Null` plus `PrefixedLineWriter`s that send `O `/`E ` lines, then `X <code>` per line (UTF-8 without BOM, `\n`). The server never touches `System.Console` (no `Launch`, no Ctrl+C handler), pipe I/O errors close only the session, cancellation ends `RunAsync` quietly, configuration errors and any exception of the session factory escape it (`RunSessionAsync` calls the factory outside both `catch (IOException)`, the one of the connection and the one of the service). `ReplPipeClient` (`ConnectAsync`, `ExecuteAsync`, `RunInteractiveAsync`, which assumes `exit`/`quit`) is the other end. `ConnectAsync` completes only once it has read `R` (`docs/adr/0024` amended, lot 036): on Unix a named pipe is a Unix socket and the connection succeeds as soon as it enters the queue of the listening socket, even when the only instance serves a session, and that queue dies with the instance at the end of the session. So it loops until the timeout (`timeout - Stopwatch.Elapsed`, clamped to [0, `int.MaxValue` ms], no explicit deadline check: `ConnectAsync(0)`/`WaitAsync(Zero)` throw `TimeoutException` themselves, and the loop has no `continue`, so no branch of the async `finally` stays uncovered), tries again on the end of the stream or an `IOException` (Unix only; `coverage/justifications.md`, `ReplPipeClient.cs:72`), throws `InvalidDataException` on another first line and `ArgumentOutOfRangeException` on a negative timeout other than `Timeout.InfiniteTimeSpan`; its wait includes the session factory. A factory that throws therefore gives the client a `TimeoutException`, never an `IOException`. **Daemon mode** (`docs/adr/0026`, nothing new on the server): `ReplPipeClient.JoinArguments` writes the arguments of a process as one REPL line (an argument is quoted when empty, when a character is `char.IsWhiteSpace`, or with `;`/`&`/`|`; `"`, `\r`, `\n` refused, since neither `CommandSequence.Scan` nor System.CommandLine's splitting has an escape), also used by `ExecuteAsync(IReadOnlyList<string>)`; `TryForwardAsync(pipeName, arguments, timeout, console, sequenceOption, token)` returns the server's code, or `null` (nothing sent) for an empty list, an argument that cannot be written, a timeout (absent and busy servers are not told apart; without a server the whole timeout is spent, as `NamedPipeClientStream` retries), so the application runs `?? starter.Start(args)`. `[sequenceOption, line]` sends the line as is, because a REPL line goes through `Start(string)`, which never reads `SequenceOption`. Null elements throw before connecting (internal `TryJoinArguments`/`ThrowIfAnyNull`); after the connection every exception leaves. A forwarded line is a REPL line, so a daemon session empties `ExitCommands`/`HelpCommands` for parity with `Start(args)` (`samples/CmdStarter.Samples.Daemon`, pipe name with `Environment.UserName`). The `Remote` tests (`ReplRemote`, `ReplDaemon`, sharing `RemoteTestServer.cs`) open real pipes with unique names and 10 s timeouts.

**Command states** (`docs/adr/0012`) work with or without the REPL.
- The library defines no state. A command (class, method group or method) carries `[AvailableInState(...)]` with the application's own values, and the application exposes its current state through `ICommandStateProvider`. The provider comes from `Starter.StateProvider`, or else from `ServiceProvider` (register it as a singleton).
- Before each `Start`, `UpdateCommandAvailability` asks for the current state:
  - an unavailable command, and its whole subtree, gets `Hidden` (combined with `[Hidden]`);
  - typing it anyway returns 1 with "Command '…' is not available in the current state.";
  - the tree is not rebuilt;
  - the rooted lonely command is refused but never unhidden;
  - commands the application added to `RootCommand` itself are left alone.
- The attribute without any provider throws `InvalidAttributeException` when the tree is built.

**Analyzer** (`CmdStarter.Analyzers`, `docs/adr/0018`): rules `CMDS0001`–`CMDS0011` and `CMDS0017` repeat at compile time checks the runtime already makes (parent cycles, several `[Parent]`, `[AutoComplete]` that yields nothing or uses an unsupported type, blank command names, invalid `[Command]` methods and plain-command handlers (`CMDS0007`/`CMDS0008`), mixed models (`CMDS0009`, also `IStarterCommand` + `[Command]` on the class), `CMDS0011` "Command class without a handler" (a `[Command]` class without `[Command]` methods and without `Handler` whose handler is not unique, or that is static, abstract or open generic), `CMDS0017` "Invalid command handler" (`Handler` missing, private, static, ambiguous, or on a group or a method), lot 037); `CMDS0012` (a command option, plain commands included, hides a global option) and `CMDS0013` (a global options container has no option) are advice only. All are warnings, so with `TreatWarningsAsErrors` they break the build of `CmdStarter.Tests.App` and of every project under `samples/` (`samples/Directory.Build.props` references the analyzer). `NameConversion` copies the library's kebab-casing; keep the two in sync (the `KebabCaseMatchesLibrary` test compares them). New rules go in `AnalyzerReleases.Unshipped.md`. The same assembly holds the **catalog generator** (`CommandCatalogGenerator`, `CatalogSource`; `docs/adr/0027`, `docs/advanced/source-generator.md`): in every compilation that has the catalog API and no hand-written `[assembly: CommandCatalog]`, it writes `CommandCatalog.g.cs` (`CommandCatalog_<assembly>` with `AddCommand<T>`, `AddMethodCommands(typeof(…))` (a static class cannot be a type argument), `AddGlobalOptions<T>`, the scan's predicates, `#pragma` for CS0612/CS0618 and the `DiagnosticId`s of listed `[Obsolete]` types). A type the generated code could not name (inaccessible, nested in a generic, open generic, `Obsolete` as error, `Experimental`, unwritable `DiagnosticId`) is left out with `CMDS0014` (Info). A plain command is listed with `AddCommand<T>`, never `AddMethodCommands`. `SymbolTypeCollector` then writes one `AddSymbolType<T>()` per distinct type of the listed commands' and containers' read/write properties, of the `[Command]` method parameters and of a plain command's handler parameters (`AddHandlerParameters`: the method `Handler` names, or every candidate when it is missing or ambiguous, no generator diagnostic) (not `CancellationToken`/`CommandConsole`, not by-ref) and of the `HandlingMethod` delegate's parameters, read by a rule: static type of the body is a concrete delegate type → its `Invoke`, else a single-method group, else `CMDS0015` (Info; the only one in the solution is `NamelessParameterCommand`'s `DynamicMethod`, on purpose). A value type it cannot write (inaccessible, `Obsolete` as error, `Experimental`, `Nullable` of such a type) is reported once with `CMDS0016` (Info: its option or argument is lost under Native AOT; none in the solution); reference types, ref-like types and pointers are not reported. Types that cannot be written as a type argument (ref-like, pointers, type parameters, inaccessible, `Obsolete` as error, `Experimental`) are skipped silently: the fallback covers them. It runs in `CmdStarter.Tests.Commands`, the demos, the benchmarks, `CmdStarter.Tests.App` and the samples. `CmdStarter.Tests.Commands.csproj` carries the only CMDS `NoWarn` of the solution (CMDS0001–0013 and CMDS0017: its commands under `Erroneous`, `Methods/Erroneous`, `PlainCommands/Erroneous`, `GlobalOptions/Filters` are wrong on purpose; decided by Main), `CMDS0014` never suppressed. `GeneratorRunner` (Analyzers.Tests) runs it and refuses any warning located in the generated tree.

## Tests

- `CmdStarter.Analyzers.Tests` compiles C# snippets against the library (`AnalyzerRunner`) and counts the diagnostics per rule. With `includeCmdStarter: false` the runner also removes `CmdStarter.Lib.dll` and `CmdStarter.Hosting.dll` from the platform assemblies, which contain them because the test project references them; `allowCompilationErrors` analyzes code that does not compile, as an editor does. `GeneratorRunner` runs the catalog generator on a snippet (same references through `AnalyzerRunner.CreateReferences`, same parse options for the driver, `allowUnsafe`).
- `CmdStarter.Lib` has `InternalsVisibleTo("CmdStarter.Tests")` (`AssemblyInfo.cs`, lot 031) for one use only: proving the symbol factories (`SymbolFactories.cs` tests: `IsGenerated`, `CreateFallback`, `Register`). Every other test keeps to the public API. The registry is static: each test uses a type of its own.
- Catalog tests (`CommandCatalogs.cs`): `CmdStarter.Tests.CatalogCommands` (normal `ProjectReference`, namespace `Catalog` excluded by default, no generator) carries a hand-written catalog that lists `Listed` and the abstract `AbstractListed` but not `Unlisted`; a broken catalog is tested with `CatalogAssembly`, a test subclass of `Assembly` passed in `Assemblies` and never loaded (an `Assembly.Load` would make every later default discovery throw). The two equivalence tests compare the generated catalog of `CmdStarter.Tests.Commands` with the scan; the whole suite runs through that catalog.
- Coverage (`measure-coverage.ps1`, coverlet on the three shipped assemblies) is 100 % of lines and branches minus the entries of `coverage/justifications.md`, one per line or branch, each with its **Decision**. A new uncovered line gets a test or a decided entry; a guard that is impossible by construction is removed rather than justified. The separate-process tests are not measured: a line they alone reach needs an in-memory test. Rebuild with `--no-incremental` before a measure that follows a restored file (an old timestamp skips the build).
- `CmdStarter.Tests` (NUnit) exercises commands defined in `CmdStarter.Tests.Commands`; `CmdStarter.Tests.Common` holds the shared interfaces and the generic `[TestCase<T>]` attributes.
- **The namespaces and attributes of the test commands are test data.** Tree-building tests depend on where a command class lives, so moving or adding a class in `CmdStarter.Tests.Commands` can change other tests' trees.
- Each test isolates its commands by setting `Namespaces`/`Classes` on a fresh `Starter`. `TestsCommon.CreateCmdStarter()` excludes the `Erroneous`, `DepencendyInjection`, `Lifecycle`, `Methods`, `Cancellation`, `ReplApp`, `States`, `Validation`, `MethodGroups`, `Hosting`, `SameLeafNames`, `DefaultValues`, `FluentTree`, `NamespaceGroups`, `Filters`, `Consoles`, `Sequences`, `Remote`, `PrivateSetters`, `BrokenGlobalOptions`, `ExecutionPaths`, `TreeBuilding`, `Catalog` and `PlainCommands` namespaces by default (a new namespace of special-purpose test commands is added to both lists) (exclusions also repeated in `Repl.SetDefaultNamespaces`). The lifecycle and DI tests instead isolate one command type with a `Classes` filter, which makes it a lonely, rooted command.
- A text assertion on output that holds control characters (`\b`, `\r`, `\0`) searches ordinally (`IndexOf(…, StringComparison.Ordinal)`): NUnit 3's `Does.Contain` compares by culture, and ICU ignores control characters, so `"hel\b\b^C"` "contains" `"el^C"` (lot 038, `ReplLineEditing`).
- Command test classes must expose read-only public properties unless the property is meant to be an option: any setter, even a private one, makes `Helper.GetProperties` turn the property into an option.
- Discovery only sees loaded assemblies, so fixtures call `TestsCommon.GlobalSetup()`, which forces `CmdStarter.Tests.Commands` to load (`DirectoryCatalog`). That catalog loads every DLL in the test output folder, so any command assembly copied there joins every default discovery.
- `CmdStarter.Tests.App` is a real CLI app (class and method commands, Microsoft DI) that `Integration/AppProcessTests` runs as a separate process (`dotnet <dll>`) to check exit codes, stdout and stderr. The test project references it with `ReferenceOutputAssembly="false"` (build order only), for the reason above.
- `samples/` holds the documented examples, one runnable project each (`samples/README.md`). `Integration/SamplesTests` and `Integration/DemosTests` run them the same way through `Integration/AppRunner` (project path relative to the repository root, optional environment variables; `RunWithInputAsync` writes stdin, then closes it, for REPL apps), so every new sample or demo needs a `ReferenceOutputAssembly="false"` reference in `CmdStarter.Tests.csproj`. `samples/CmdStarter.Samples.Testing.Tests` is a second NUnit project, run by the same `dotnet test CmdStarter.sln`.
- `Integration/DocumentationTests` (category `Documentation`) guards `README.md`, `PKG-README.md`, `samples/README.md` and every `docs/**/*.md` (`RepositoryPaths.Root` finds the repository): every relative link must exist on disk; every ```` ```csharp ```` block must be preceded by `<!-- snippet: path/from/root -->` and each of its trimmed lines must be a line of that file (`// ...` allowed); every inline-code token `Type.Member[.Member]` whose first segment is a public type of `CmdStarter.Lib`/`CmdStarter.Hosting`, and every `[Attribute]`, must exist (reflection, generics by name). The last two skip `docs/adr/` and `docs/migration/`, so check those by hand. Each test first runs its checker on built inputs. Code in a page therefore comes from a real, compiled file, and private or internal members cannot be named in backticks.

## Conventions

- File-scoped namespaces only (`namespace X;`), enforced by `.editorconfig`. Namespaces: `CyberInternauts.CmdStarter` for the library (assembly `CmdStarter.Lib`, package `cints.CmdStarter`), `CyberInternauts.CmdStarter.<Project>` for the other projects (`Tests`, `Tests.Commands`, `Demo.SimpleInjector`…), so test namespace filters use these names.
- Ordinal string comparisons in the library.
- No public `string[]`/`List<string>` overload twins: a collection expression is then ambiguous (CS0121). `Starter(IEnumerable<string>)` and `ReplStarter(IReplInputProvider, IEnumerable<string>)` are the constructors with namespaces (lot 038); they copy the sequence.
- Architecture decisions are recorded in `docs/adr/` (index in `docs/adr/README.md`); breaking changes go in `docs/migration/0.9-to-1.0.md`.
- The user documentation is `docs/` (`index.md`, `getting-started.md`, `concepts/`, `guides/`, `advanced/`), in English, with a `## See also` per page. A page states only what a test or a sample shows; a new behaviour gets its test first. The DocFX site (`docfx.json`, `toc.yml`, `docs/toc.yml`, root `index.md`, `api/index.md`; never published) reads the API from the built assemblies, so `dotnet build CmdStarter.sln`, `dotnet tool restore`, then `dotnet docfx docfx.json --warningsAsErrors` (0 warning). `InvalidFileLink` is downgraded to info (`rules` in `docfx.json`) because links to `samples/` leave the DocFX content; `DocumentationTests` checks them.
